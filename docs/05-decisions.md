# 决策记录

> 状态说明：**提议**表示方案建议，待确认；**待定**表示需要产品负责人拍板；**已定**表示已确认。

## 提议中的架构决策

### D-01 不自研 agent loop

- 状态：已修订。v1 改为自研精简循环，原因见 [v1 设计](09-v1-design.md) V1-01
- 内容：使用成熟的 agent harness（见[技术方案](03-architecture.md) 5.3），平台只定义任务协议并做适配。
- 理由：harness 是模型厂商和开源社区投入最重的部分，自研很难追上；产品的差异化在需求、模板、验证、发布和计费。
- 代价：受 harness 的能力和许可约束；需要维护适配层。

### D-02 沙箱必须达到 microVM 或 gVisor 级隔离

- 状态：提议
- 内容：多租户环境下运行 AI 生成的代码，不把共享内核的普通容器当作唯一的隔离手段。
- 理由：执行的代码不可信，一次容器逃逸会波及所有租户。
- 代价：冷启动和成本略高，需要预热池和快照。

### D-03 Git 是唯一事实源，沙箱无状态

- 状态：提议
- 内容：所有代码变更都以 commit 形式进入用户仓库；沙箱随时可以销毁重建。
- 理由：回滚、审计、逃生舱、故障恢复都依赖这一点。

### D-04 MVP 只做一条黄金路径

- 状态：提议
- 内容：前端单页应用（Vite + React + TypeScript）→ GitHub Pages。
- 理由：这是"零 IDE"可行度最高的项目类型。先把成功率和成本测准，再扩展。

### D-05 验收测试锁定，编码 agent 无权修改

- 状态：提议
- 内容：验收标准经用户确认后生成验收测试，只读挂载进沙箱；编排服务拒绝任何修改 `tests/acceptance/` 的 PR。
- 理由：防止 agent 通过修改测试来"让测试变绿"。

### D-06 凭证不进沙箱，agent 只能推分支

- 状态：提议
- 内容：Git token、模型 API key、用户密钥只存在于平台代理层，在出口注入；agent 推送用的 token 不带 Workflows 权限；合并、发布等有副作用的操作由编排服务在用户确认后执行。
- 理由：防止提示词注入或恶意依赖窃取凭证，也防止 agent 改掉 CI 检查或直接动生产。

## 需要拍板的问题

| 编号 | 问题 | 选项 | 影响 | 建议 |
|---|---|---|---|---|
| Q-01 | 目标市场 | 海外 / 国内 / 两者都做 | 模型、合规、Git 平台、发布目标 | 最先确定，其他决策都依赖它 |
| Q-02 | 首要用户 | A 非技术个人 / B 企业业务人员 / C 开发者 | 产品形态、定价、销售方式 | 用 A 验证链路，用 B 做商业化 |
| Q-03 | 主力模型 | Claude 等前沿模型 / 国产模型 / 多模型 | 成功率、成本、合规 | 由 Q-01 决定范围，用评测集实测后定 |
| Q-04 | Agent 运行时 | Claude Agent SDK / Managed Agents / 开源 harness | 开发速度、可移植性、私有化能力 | 海外 MVP 选 SDK 或 Managed Agents；国内或私有化选开源 |
| Q-05 | 沙箱 | 托管服务 / 自建 | 上线速度、成本、合规 | MVP 用托管服务，私有化时再自建 |
| Q-06 | 用户仓库归属 | 用户自带 GitHub 账号 / 平台代建并托管仓库 | 非技术用户的门槛，对比平台承担的滥用和成本风险 | MVP 要求用户自带账号；确定面向非技术用户后再评估托管 |
| Q-07 | 商业模式 | 订阅加 credit / 按成功交付 / 私有化授权 / 人工兜底服务 | 毛利结构 | 等 Phase 0 的成本数据出来再定 |
| Q-08 | 首个垂直场景 | 活动页 / 企业官网 / 数据看板 / 内部工具 / 小程序 | 模板方向 | 结合 Q-02 的用户访谈确定 |
