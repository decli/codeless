# v1 设计：对话式编程 agent

- 日期：2026-10-19
- 状态：已实现（本文描述仓库根目录下的 `codeless/`、`web/`）
- 依据：[行业 agent 调研](08-agent-research.md)，[POC 验证结果](06-poc-findings.md)

## 1. 目标

用户在网页上用对话描述想要的程序，agent 在隔离沙箱里写代码、运行、实时预览、发现问题自己修，用户随时插话或改需求。对标 Claude Code、Codex 这类成熟 coding agent 的工作方式，区别是**基座模型由用户配置**：国产模型、Claude、OpenAI、本地模型都能接。

首先支持 Python 和 Node.js：命令行程序、数据脚本、Web 后端、前端应用、小游戏都在范围内。

## 2. 和 POC 的差距

POC 验证了「需求 → 沙箱写码 → CI 发布」这条链路能通，但它是一次性的流水线，不是 agent：

| 方面 | POC（v0） | v1 |
|---|---|---|
| 交互 | 提交需求后等结果，多轮对话是重新跑一遍流水线 | 持续对话；agent 工作时可以插话、随时停止 |
| 语言 | 只有 Python 静态站 | Python 3.12 + Node.js 22，内置 React/Vite、Express、FastAPI 起步模板 |
| 运行 | 测试跑完容器就销毁 | 每个项目一个常驻沙箱，后台进程、日志、端口都可管理 |
| 预览 | CI 部署后才能看到 | 开发服务器实时预览，热更新直接生效 |
| 验证 | 只看 pytest 结果 | 每轮结束后由系统检查进程、端口、页面和资源、浏览器控制台，有问题自动交回 agent 修 |
| 模型 | 只支持 OpenAI 兼容协议，环境变量配置 | 两种协议，多个模型档案，界面上配置和切换，按用量计费 |
| 回滚 | 无 | 每轮自动保存检查点，可以查看改动、撤销本轮、恢复到任意检查点 |
| 上下文 | 无管理，长任务会超窗口 | 动态上下文块、工具输出截断落盘、超阈值整段摘要压缩 |
| 依赖服务 | Gitea、Actions runner、nginx | 只要 Docker；CI 发布链路留在 POC 里，后续按需接回 |

## 3. 架构

```
浏览器 ── /api（REST + SSE）──► 编排服务（FastAPI，codeless/）
   │                              ├─ agent 循环（每个项目一个线程）
   │                              ├─ 模型适配层：OpenAI 兼容 / Anthropic
   │                              ├─ 工具 → 沙箱（docker exec）
   │                              ├─ 检查点（宿主侧 git）
   │                              └─ 预览代理 + 自检（HTTP、无头浏览器）
   └─ <id>.localhost ─► 预览代理 ─► 沙箱容器里的开发服务器（内部网络）
                                        └─ 出网只能经白名单代理到包管理源
```

- **编排服务**：Python，单进程。项目状态都在 `data/` 下的文件里，重启后恢复对话、时间线和预览进程。
- **前端**：React + TypeScript + Vite，构建产物由编排服务直接提供。
- **沙箱**：每个项目一个 Docker 容器，工作区以目录挂载。内部网络加白名单代理，限 CPU、内存和进程数，闲置自动停掉。容器里没有 API Key、没有 git 凭证，git 操作在宿主侧做。
- **时间线**：界面上的每条记录（消息、思考、工具调用、检查点）都是一个条目，变化以带序号的增量推送，断线后按序号续传。

## 4. agent 循环

一轮从用户发消息开始：

1. 拼上下文：系统提示词固定不变（利于缓存，也满足 Anthropic 思考块的校验），会变的信息放在本轮用户消息末尾的 `<context>` 里：文件列表、AGENTS.md、后台进程状态、用户浏览器里上报的运行时错误、用户回滚等事件。
2. 流式调用模型，思考、正文、工具调用实时显示。
3. 执行工具，结果回给模型；用户这时发来的消息作为「插话」插进下一次请求。
4. 模型不再调用工具时，如果这一轮动了代码且有预览进程，系统自动检查预览。发现问题把结果作为「[自动检查]」消息交回 agent 修，最多 2 次（可配置）。
5. 收尾：保存检查点，统计用量和花费。

工具共 11 个，参照 Claude Code 的工具集做了精简：`list_files`、`read_file`、`write_file`、`edit_file`、`search`、`bash`、`start_process`、`process_logs`、`stop_process`、`check_preview`、`todo_write`。

为弱模型做的容错：

- 工具参数解析容忍代码块包裹、尾逗号、双重编码；解析失败把原因告诉模型让它重发。
- `edit_file` 精确匹配失败时依次尝试忽略行尾空白、忽略缩进（并修正新内容缩进），还不行就返回文件里最接近的片段。
- 写 Python、JSON 文件后立刻做语法检查。
- `bash` 拒绝开发服务器这类不会退出的命令，引导改用 `start_process`；超长输出截断并落盘，模型需要时再读。
- `<think>` 标签写在正文里的模型（本地 R1、QwQ 等）自动拆出思考内容。
- DeepSeek、Kimi 等思考模型在工具循环里要求回传 `reasoning_content`，适配层按服务的报错自动调整回传策略。

## 6. 关键决策

需求里留给我判断的决策点，选择和理由如下。

### V1-01 自研 agent 循环，不套用现成 harness

- 选择：自研一个精简的循环和工具集。
- 理由：基座模型要用户可配置。Claude Code、Codex 的 harness 绑定自家模型或协议；OpenHands、Cline 能接任意模型，但体量大、和预览、自检、时间线这些产品能力耦合不上。精简循环加针对弱模型的容错层，更容易把成功率做上去。这修正了早期 [D-01](05-decisions.md) 的提议。
- 代价：工具和提示词要自己持续调优；子代理、MCP 等高级能力要自己补。

### V1-02 模型适配层只做两种协议

- 选择：OpenAI Chat Completions 兼容协议 + Anthropic Messages 协议。
- 理由：国内主流服务（DeepSeek、通义、Kimi、智谱、豆包、硅基流动）和 OpenRouter、Ollama 都提供 OpenAI 兼容接口；Claude 用原生协议才能用上思考、提示缓存。内部消息格式和协议无关，换模型不丢历史。
- 代价：OpenAI 的 Responses 接口等新协议暂不支持。

### V1-03 沙箱用 Docker 容器 + 白名单出网

- 选择：每个项目一个常驻容器，内部网络，出网只经白名单代理到包管理源；提供不隔离的本地进程模式用于调试。
- 理由：自托管、单机部署最容易落地；常驻容器让开发服务器和热更新可用。和调研里行业从浏览器内运行时转向每会话隔离环境的方向一致，而且天然支持 Python。
- 代价：普通容器不是多租户级隔离（[D-02](05-decisions.md) 仍然成立），对外服务前要换 gVisor 或 microVM。

### V1-04 预览用子域名

- 选择：`<项目 id>.localhost:8000` 经编排服务反向代理到沙箱。
- 理由：POC 踩过子路径部署导致绝对路径 404 的坑；子域名让站点跑在根目录，也让预览和管理界面不同源，预览里的脚本调不了管理接口。`*.localhost` 浏览器自动解析到本机，不用改 hosts。

### V1-05 验证由系统强制执行

- 选择：每轮结束后系统自己检查预览，不依赖模型自觉调用。
- 理由：调研里头部产品的核心竞争力是运行时反馈闭环；弱模型经常写完就宣布完成。把检查放到系统侧，任何模型都能享受到。

### V1-06 上下文压缩用整段摘要

- 选择：超过窗口约 75% 时，把全部历史换成一条摘要再接着做。
- 理由：保留最近几轮原文的半压缩方式，会让 Anthropic 的思考块和改写后的历史对不上而被拒；整段摘要对两种协议都安全。

### V1-07 检查点用宿主侧 git

- 选择：工作区本身是 git 仓库，每轮结束提交一次；恢复用 `read-tree` 生成新提交，历史不丢。
- 理由：简单可靠，用户也能直接用 git 查看；git 在宿主侧执行，沙箱里拿不到任何凭证。

### V1-08 先不做 CI 发布

- 选择：v1 聚焦对话、运行、预览、自修复；产出可以下载源码。POC 里的 Gitea + CI 发布链路保留在 `poc/`。
- 理由：调研和 POC 都表明，成功率取决于运行时反馈闭环；发布是在作品能用之后的事，后续可以作为一个工具接回来。

## 7. 界面

统一的设计规范，所有页面共用（`web/src/styles/tokens.css`）：

- 字体：系统中文字体（苹方、微软雅黑），代码用等宽字体。字号 6 档：12、13、14、16、20、28。
- 间距以 4 为基数；圆角 6、8、12 三档；控件高度 28、32、40 三档，同一行的控件同高。
- 颜色：中性灰阶加单一靛蓝强调色；红、黄、绿只用于状态。支持浅色、深色和跟随系统。
- 图标统一用 lucide，线宽一致。

布局：左侧项目列表，中间对话，右侧工作台（预览、代码、改动、终端），对话和工作台之间可以拖动调整宽度；窄屏下对话和预览切换显示。

## 8. 测试

`make test` 不需要真实模型和 Docker：用假模型服务模拟两种协议的流式接口，按剧本回复，跑通写代码、运行、自检、自动修复、插话、停止、回滚的完整流程。`make test-all` 额外跑 Docker 沙箱的隔离测试（Key 不进沙箱、看不到宿主数据、白名单外的网站访问不了）和无头浏览器自检。

## 9. 后续

1. 评测集：按调研 5.1 节，用同一批真实需求测不同模型的首次成功率、自修复成功率、轮数和花费，持续调工具和提示词。
2. Plan 模式和危险操作确认。
3. 发布：把 POC 的 CI 发布链路做成一个工具，一键部署到 Pages 或推送到 GitHub / GitLab。
4. MCP：让用户接入自己的工具和数据源。
5. 多租户：沙箱换 gVisor 或 microVM，加账号体系。
